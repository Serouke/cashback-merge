# Cashback Merge

Мини-игра в духе 2048 на поле с плитками кэшбэка: одинаковые плитки объединяются (1% + 1% = 2%, затем 4%, 8%, 16%, 32%), число ходов ограничено. По самой большой плитке в конце партии игрок получает награду. Перед запуском кампании её проверяют симуляцией: максимальную награду должна получать ограниченная доля игроков, иначе статус кампании — FAILED.

## Сборка и тесты

Нужен .NET SDK 10.

```
dotnet build
dotnet test
dotnet format --verify-no-changes
```

Обязательные тесты из задания лежат в `tests/CashBackMerge.Tests/Mandatory`, по папке на каждую часть: `Mr1`, `Mr2`, `Mr3`.

## Запуск

Начальное поле:

```
dotnet run --project src/CashBackMerge.App -- show --config campaign.json --seed 42
```

```
. 1 . .
. . . .
. . 1 .
. . . .
Оставшиеся ходы 100
Счёт 0
```

Точка — пустая клетка. Одинаковые конфиг и seed всегда дают одинаковое поле.

Симуляция кампании:

```
dotnet run --project src/CashBackMerge.App -- simulate --config campaign.json --players 10000 --strategy random --seed 42 --output report.md
```

`--players` — сколько партий сыграть, `--strategy` — как игрок выбирает ход (сейчас есть `random`), `--output` — куда записать отчёт; без него отчёт печатается в консоль. Одинаковые конфиг, seed и стратегия дают одинаковый отчёт.

Сыграть самому:

```
dotnet run --project src/CashBackMerge.App -- play --config campaign.json --seed 42
```

Ходы — W/A/S/D или стрелки, Q — выход. После каждого хода видны поле, оставшиеся ходы, счёт и награда за текущую самую большую плитку. В конце игра печатает команду для повтора этой партии.

Повторить партию по seed и списку ходов:

```
dotnet run --project src/CashBackMerge.App -- replay --config campaign.json --seed 42 --moves LURDLR
```

Ходы записываются буквами: L — влево, R — вправо, U — вверх, D — вниз. Команда печатает поле после каждого хода и итог партии.

Код возврата: 0 — команда отработала или симуляция дала OK, 2 — симуляция дала FAILED, 1 — ошибка в аргументах, файле или конфиге. Отдельный код для FAILED позволяет скрипту или CI не пропустить несбалансированную кампанию.

## Конфиг

Пример лежит в `campaign.json`.

| Поле | Тип | Правило |
|---|---|---|
| `boardSize` | число | Размер поля от 2 до 10. Если поле не указано, берётся 4 |
| `movesLimit` | число | Лимит ходов, больше нуля |
| `spawnRules` | список | Правила появления плиток, хотя бы одно |
| `spawnRules[].cashback` | строка | Плитка в процентах: положительная степень двойки |
| `spawnRules[].probability` | строка | Вероятность: число с точкой, больше нуля, не более 9 знаков после точки. Сумма — ровно 1 |
| `rewardTable` | список | Таблица наград, хотя бы одна строка |
| `rewardTable[].cashback` | строка | Плитка в процентах: положительная степень двойки, без повторов |
| `rewardTable[].reward` | строка | Награда: неотрицательное число |
| `maxRewardCashback` | строка | С какой плитки награда считается максимальной. Такая строка должна быть в `rewardTable` |
| `maxRewardAllowedRate` | строка | Какая доля игроков может получить максимальную награду: число от 0 до 1 |

Все поля, кроме `boardSize`, обязательны. Проценты, вероятности и награды записаны строками и хранятся в `decimal`, чтобы не терять точность: на `double` сумма `0.7 + 0.2 + 0.1` не равна 1. Неизвестные поля пропускаются.

Если конфиг неверный, программа печатает все найденные ошибки сразу:

```
config.movesLimit.notPositive movesLimit: должно быть положительным значением
config.maxRewardCashback.notInTable maxRewardCashback: процента 64 нет в rewardTable
```

## Ходы

Ход делается в одну из четырёх сторон. Плитки сдвигаются до упора, две одинаковые плитки, оказавшиеся рядом, объединяются в одну вдвое больше. Примеры для строки при ходе влево:

| До хода | После хода | Очки за ход |
|---|---|---|
| `1 1 . .` | `2 . . .` | 2 |
| `1 1 1 .` | `2 1 . .` | 2 |
| `1 1 1 1` | `2 2 . .` | 4 |
| `2 2 4 4` | `4 8 . .` | 12 |
| `1 1 2 .` | `2 2 . .` | 2 |

- Плитка объединяется не больше одного раза за ход: `1 1 2 .` даёт `2 2 . .`, а не `4 . . .`.
- Очки за ход — сумма плиток, получившихся при объединении. Счёт партии — сумма очков за все ходы.
- Ход, который ничего не сдвинул, не тратит лимит и не создаёт новую плитку.
- После хода, изменившего поле, появляется ровно одна новая плитка.
- Партия заканчивается, когда лимит ходов исчерпан или ни один ход не меняет поле. Плитка 32% партию не заканчивает.

## Награды и симуляция

Награда берётся из самой старшей строки `rewardTable`, процент которой не больше самой большой плитки. Если плитка меньше всех строк, награда 0. Поэтому плитка 64% получает награду строки 32. Максимальную награду получает игрок, у которого самая большая плитка не меньше `maxRewardCashback`.

Симуляция раздаёт каждому игроку свой seed и играет все партии до конца. Стратегия `random` выбирает одну из четырёх сторон наугад и выбирает снова, если ход ничего не сдвинул. Статус OK, если доля игроков с максимальной наградой не больше `maxRewardAllowedRate`, иначе FAILED.

## Как сбалансировать кампанию

Кампания из `campaign.json` слишком щедрая. Объединения не меняют сумму плиток на поле, растёт она только за счёт новых плиток — в среднем на 1.15% за ход. Чем больше ходов, тем чаще собираются крупные плитки. Тот же конфиг с другим лимитом, 10 000 игроков, seed 42:

| Лимит ходов | Максимальная награда | Статус |
|---|---|---|
| 30 | 0.05% | OK |
| 40 | 9.87% | OK |
| 50 | 44.91% | FAILED |
| 100 | 92.59% | FAILED |

Граница лежит между 40 и 50 ходами. При 30 ходах главный приз почти недостижим: проверку кампания проходит, но играть в неё скучно.

Второй рычаг — размер поля, `boardSize`. На маленьком поле плитки быстро упираются друг в друга, и партия заканчивается раньше лимита: ходить некуда. Тот же конфиг со 100 ходами:

| Поле | Максимальная награда | Статус |
|---|---|---|
| 3×3 | 9.12% | OK |
| 4×4 | 92.59% | FAILED |
| 5×5 | 99.93% | FAILED |

Это эмпирическая проверка, а не гарантия: она верна для конкретного конфига, seed, числа игроков и стратегии. Стратегия `random` играет хуже живого человека, поэтому настоящие игроки будут получать максимальную награду чаще.

## Структура

| Проект | Что внутри |
|---|---|
| `src/CashBackMerge.Core` | Модель игры, конфиг, движок ходов, награды, симуляция и отчёт. О консоли и файлах не знает |
| `src/CashBackMerge.App` | Консольное приложение: аргументы, чтение и запись файлов, вывод |
| `tests/CashBackMerge.Tests` | Тесты |

Где что в коде:

| Класс | Что делает |
|---|---|
| `LineMerger` | Сдвигает одну линию влево и объединяет плитки |
| `BoardMover` | Сдвигает поле в любую сторону, сводя ход к ходу влево |
| `GameEngine` | Ход целиком: сдвиг, новая плитка, лимит и счёт; проверка конца партии |
| `RewardTable` | Награда по самой большой плитке и признак максимальной награды |
| `RandomStrategy` | Стратегия, которая выбирает сторону хода наугад |
| `GameRunner` | Одна партия по seed: возвращает самую большую плитку и счёт |
| `CampaignSimulator` | Все партии симуляции и сборка отчёта |
| `MarkdownReportFormatter` | Отчёт в Markdown |
| `GameReplay`, `MoveNotation` | Повтор партии по seed и списку ходов; запись ходов буквами |
| `ConsoleGame` | Консольная игра: ход с клавиатуры, поле, оставшиеся ходы и награда |

## Принятые решения

- На старте на поле две плитки, они выбираются по тем же правилам, что и новые.
- Плитка и клетка для неё выбираются целыми числами: вероятность `0.85` — это 85 билетов из 100.
- Формулу счёта ТЗ не задаёт. Взята формула из 2048: объединение приносит столько очков, сколько стоит новая плитка.
- Потолка у плиток нет: две плитки 32% объединяются в 64%.
- Если ни один ход не меняет поле, партия заканчивается раньше лимита.
- Награда ищется как «самая старшая строка таблицы, не больше плитки». При поиске по точному совпадению плитка 64% осталась бы без награды.
- Seed каждой партии выдаёт главный генератор симуляции, поэтому любую партию можно повторить по её seed.
- Статус считается без деления: число игроков с максимальной наградой сравнивается с произведением допустимой доли на число игроков. Так граница не зависит от округления.
- Числа в отчёте печатаются с точкой, строки разделяются символом `\n`: отчёт одинаков на Windows и Linux.
- `replay` точно повторяет партии из `play`: ходы приходят снаружи, и случайность тратится только на новые плитки. Партию из симуляции так не повторить — там стратегия `random` берёт числа из того же источника. Её повторяет запуск `GameRunner` с тем же seed.
- В `play` на Windows клавиши W/A/S/D работают при любой раскладке: игра смотрит на саму клавишу, а не на введённую букву.
